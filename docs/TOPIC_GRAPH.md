# 主题图谱设计

状态：0.5.0 已实现只读主题树、主要/辅助映射、三入口联动和决定记忆；自由拖拽与完整图编辑器仍不在第一版范围。详细流程见 `docs/CONTENT_WORKFLOW.md`。

## 1. 决策摘要

- 给运营者看的主界面是可搜索、可折叠的树。
- 底层是概念图：每个主题有一个主父级，同时允许跨分支相关关系、同义表达和历史决定。
- 建设方式是“先搭稳定骨架，再随真实信号逐步扩展”，不是一次预生成 100–200 个文章标题，也不是完全边写边临时分类。
- 图谱用于看清覆盖、发现缺口、避免重复和保存拒绝记忆；它不把文章数量当目标。

## 2. 用户看到的结构

层级允许深浅不一，不强迫每个分支都有相同级数。示意：

- 激光笔
  - 使用场景
    - 钓鱼
      - 驱赶水边鸟类：已有文章，点击标题可打开原文
      - 户外紧急信号：与“户外 / SOS”跨分支关联
      - 用光线吸引鱼：待证据假设，未验证前不能成为写作任务
  - 选择与购买
  - 性能与原理
  - 操作与故障
  - 安全与法规
  - 产品与型号证据

“钓鱼”“天文”“演示”等是场景；再下一层应描述真实用户任务或问题，而不是机械拼接关键词。示例只说明结构，不代表每个主题都已被需求、安全或事实证据验证。

## 3. 底层对象

### 规范主题

每个主题保存稳定标识、首选名称、说明、类型、状态、主父级和边界。主题身份主要由用户问题、搜索意图和页面职责决定，不能只看关键词是否不同。

### 别名与关联

同义词、长尾措辞和语言变体作为别名或证据挂在同一主题下。跨场景关系保存为 related，不复制主题来强行组成纯树。

### 文章覆盖

文章与主题是显式关联，保存文章 URL、覆盖角色、映射依据、置信度和人工确认状态。树中现有文章标题必须是可点击链接。标题或标签相似只能生成待复核映射，不能自动宣称文章已经覆盖某查询。

新文章候选的重复/子题覆盖只对照活动 Blog 正文。Product 仍显示在图谱并用于产品页与内链
机会，但产品规格、标签或元数据不能冒充一篇旧文章已经完整回答信息意图。

每篇文章最多有一个“主要文章主题”，同时可以关联多个“辅助知识主题”。主要主题由页面的核心用户任务决定，title、H1、slug、开头承诺、正文主要篇幅和结论共同提供判断依据；H1/H2 层级不能单独决定主题身份。

树中的产品链接同样来自 CMS 内容项 canonical。LaserPointerHub 产品使用导入 SKU 生成
`/p-{SKU}.html`，不能用产品 slug 猜 `/products/{slug}`；非活动内容不进入图谱映射。

安全、波长、功率、法规和电池等内容作为辅助知识时可以合理出现在多篇文章中，不占用新的文章主题名额，也不主导蚕食判断。如果页面本身主要回答安全、波长或功率问题，它们就是该页主要主题，正常参与覆盖与重复检查。

### 发现候选

新主题候选保存来源证据、建议父级、重复检查、缺失证据和状态。它先进入待确认队列，不直接进入正式图谱、机会或执行方案。

开放调度的十二类来源入口只是发现检查表，不要求候选硬套当前树分支。只要手持激光笔仍是核心对象且未与活动博客同主意图/正文覆盖，意图不同的相邻细化可以进入折叠候选池；自动分支只提供旧 Plan 任务卡与建议父级。末端主意图聚类只合并同一页面职责的换说法，并与已有候选记忆去重，不因共享“电池、散热、安全”等大方向而合并不同任务。

### 决定记忆

接受、拒绝、延后、移出边界及“合并到已有主题”的决定保留理由、时间和证据。以后再次发现相同意图时，系统更新原记录，不重复制造一张新机会卡。

## 4. 状态语言

详细状态可以在系统内部用于审计和推断，但不能要求运营者日常维护。树状主界面只显示三个简单结果，并同时使用文字和图标：

- 已有文章。
- 值得扩展。
- 暂无机会。

运营者只做三个决定：要做、不再推荐、暂时跳过。“部分覆盖、待证据、已完成、边界外、暂时饱和”等由系统保存或派生，只有打开详情时才解释，不作为一排待选择状态。

## 5. 工作流

### 初次建图

1. 建立少量稳定主干。
2. 用现有 65 篇文章的标题、slug、摘要、标签和正文生成候选映射。
3. 明确标记程序推断；低置信映射进入人工抽查，不自动改文章。
4. 把同一意图的多篇文章放进同一主题家族，暴露可能重复，而不是继续拆出新主题。

### 新发现同步

1. 规范化新候选并检查别名、已有规范主题、文章覆盖和历史决定。
2. 如果只是已有主题的新措辞，附加证据，不新建节点。
3. 如果是潜在新意图，放入待确认队列并建议位置。
4. 已确认边界内的新意图进入资格判断；明显扩展到全新受众、用途或站点目的时才请求运营者确认边界。
5. 运营者可以选择要做、不再推荐或暂时跳过；不操作也不会阻断其他功能。

### 三入口联动

主题候选可以来自 GSC 信号、图谱缺口或边界扩展，三者都必须先经过规范化、覆盖检查和历史决定检查。没有 GSC 查询不再阻止图谱缺口和边界扩展调研；没有 query→page 联合数据时，仍然不得把查询归属到某个旧页面。

### 边界扩展调研

当 GSC 信号弱、图谱已知缺口少或近期结果不断重复时，系统从一个现有分支建立档案，并按以下维度轮换研究：

1. 新受众与角色，包括使用者、购买/决策者、经验水平和职责。
2. 新场景、目标与生命周期，包括期望结果、使用前/中/后任务和会改变问题的使用条件。
3. 故障、限制、误用与替代，包括什么时候不该使用以及应改用什么。
4. 选择、购买与验证标准，包括规格核实、测量、认证、总成本和购买后风险。
5. 产品、技术、兼容与生态变化。
6. 法规、安全、地区和行业变化。
7. 相邻但仍在站点边界内的问题；替代或配套方向仍须服务既定站点目的。

搜索意图、地区/语言、经验角色、季节/环境条件和内容形式作为横向筛选器使用，不新建一级维度。筛选器只细化研究问题和适用边界，不能单独创建图谱节点或文章候选。

每次运行保存分支、维度、横向筛选器快照、查询、来源、发现概念、重复匹配和无结果记录。下一轮优先研究未覆盖或已经过期的“分支 × 维度”，不重复宽泛查询。运营者也可以在任一节点点击“从这个方向继续调研”。

### 人工细化

运营者可以在任一节点选择“从这个方向继续调研”，系统只研究该分支；也可以添加一个人工想法或标记站点边界。人工想法仍需证据和重复门槛，不能因人工输入而自动发布。

## 6. 怎样判断饱和

饱和按分支判断，同时满足以下条件才暂时标记：

- 没有通过资格门槛的未覆盖主题。
- 最近按不同扩展维度进行的定向调研只得到已覆盖主题、别名、已拒绝项或证据不足项。
- 现有文章没有明确的表现问题或内容缺陷需要更新。
- 没有新产品、法规、季节、受众问题或 GSC 信号需要重新打开该分支。

饱和后系统等待新信号，不强行凑出两篇新文章或两篇旧文章。站点整体也不因此被宣布“永久穷尽”。

## 7. 分阶段实现

### A. 只读树

自动生成骨架和文章映射，支持搜索、折叠、文章链接、状态筛选和节点详情。这一步不提供自由拖拽，工作量可控。

### B. 待确认队列

接入 GSC、图谱缺口和边界扩展候选、规范主题去重和“要做 / 不再推荐 / 暂时跳过”记忆，让重复推荐先得到解决。

### C. 可选人工操作

增加“从这个方向继续调研”、移动建议父级、添加想法和标记边界；再把分支缺口接到“新写 / 更新”执行入口。

### D. 边界扩展引擎

增加分支档案、补全后的七个扩展维度、横向筛选器、研究历史和停止条件；研究预算范围遵循 `docs/CONTENT_WORKFLOW.md`。这一步复用现有外部来源服务，但不再只接受明确 GSC 查询作为种子。

## 8. 方法依据

- W3C SKOS 提供 broader、narrower、related、首选名和别名等受控概念建模基础：https://www.w3.org/TR/skos-reference/
- Google 建议站点有明确受众和主要目的，并警告为搜索流量批量制造许多主题内容：https://developers.google.com/search/docs/fundamentals/creating-helpful-content
- Google 将以操纵排名为目的批量生成低价值页面列入 scaled content abuse：https://developers.google.com/search/docs/essentials/spam-policies#scaled-content
- Topic cluster 与关键词聚类是行业组织方法，不是 Google 规定；同一或相近意图应优先评估一个页面是否足够：https://ahrefs.com/blog/topic-clusters/ 和 https://ahrefs.com/blog/keyword-clustering/
- 关键词重合本身不等于蚕食，核心仍是页面是否争夺同一意图：https://ahrefs.com/blog/keyword-cannibalization/
- HBR 的 customer job map 与 Digital.gov 的用户旅程方法用于补全目标结果、任务阶段、痛点和使用条件：https://hbr.org/2008/05/the-customer-centered-innovation-map 和 https://digital.gov/guides/research-collaboration/user-needs/journeys
- Baymard 的电商可用性研究表明兼容性、替代产品和配套产品对应不同用户问题：https://baymard.com/blog/ecommerce-compatibility-databases 和 https://baymard.com/blog/product-page-suggestions
- 上述方法只用于产生研究问题；能否成为文章仍由需求、覆盖、边界和证据门槛决定。
- 已确认的两阶段方法与边界扩展细则见 `docs/CONTENT_WORKFLOW.md` 和 ADR-0009。
