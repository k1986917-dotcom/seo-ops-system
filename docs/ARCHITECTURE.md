# 系统架构

## 1. 总体结构

```text
┌──────────────────────────────────────┐
│ 浏览器：1导入 / 2调研 / 3建议 / 4制作 / 5图谱 / 次要设置 │
└──────────────────┬───────────────────┘
                   │ HTTP（localhost）
┌──────────────────▼───────────────────┐
│ FastAPI 应用层：路由 · 表单 · 本机边界 · 展示 │
└───────┬───────────────────┬──────────┘
        │                   │
┌───────▼────────┐  ┌───────▼──────────────────┐
│ 确定性核心       │  │ services/ 外部适配层       │
│ 导入/质量/门槛/排序│  │ SerpAPI/Firecrawl/Tavily/AI │
└───────┬────────┘  └─────────────┬────────────┘
        │                         │
┌───────▼─────────────────────────▼────────────┐
│ SQLite（派生状态）+ 不可变文件快照 + 本地 .env │
│ Evidence / Rules / Opportunities / Actions / Outcomes │
└──────────────────────────────────────────────┘
```

## 2. 五个逻辑层

### 数据层

保存原始快照、哈希、导入批次和标准化记录。原始文件默认不可变；仅当运营者明确删除某次错误 GSC 导入时执行受控物理删除。外部执行层完成后，供应商响应也必须进入不可变快照，而不是只保存 AI 摘要。

每个站点同一时刻只有一个 GSC 导入批次生成当前机会；另用独立可信标记累计后续正常历史窗口。默认保留不可变快照；运营者明确删除某次错误 GSC 导入时，物理删除该批次快照、指标及只依赖它的派生分析，且不自动恢复旧批次。

### 证据与质量层

GSC、CMS、SERP、Trends、网页内容和研究线索标成不同证据类型。每条外部证据先由 `external_runs` 保留脱敏响应快照、参数、哈希、用量和失败状态，再派生 `evidence_items`。`services/data_quality.py` 先检查独立窗口与官方 GSC 异常。

### 规则层

规则包含资格门槛、诊断条件、行动模板、证据要求、版本、理由、官方来源、复查日期和失败模式。`gsc_signal_stability 0.2.0` 会改变置信权重或把曝光相关候选降为补证据。

### 决策层

先执行 hard gates，再对合格机会排序，最后组合最多 2 篇旧文章 + 2 篇新文章；任何一类不足时允许为 0。分数只用于比较，不声称是成功概率。当前公开入口在 `opportunities/quality_engine.py`，复用基础候选生成器后追加数据质量门槛，再由 `opportunities/engine.py` 分配文章席位。

### 执行与学习层

执行层分为“关键词与主题调研”和“文章制作”两阶段。0.8.0 用五步顺序界面承载两阶段：调研候选只在文章建议页决定，执行后只在文章制作页出现；新文章先整理 A–H 素材并由运营者决定是否手工补充。发布后任务退出当前页面并保留后台审计，系统不自动发布。

### 主题规划层

界面以可折叠树呈现站点主题骨架和真实覆盖文章；底层保存主父级、跨分支关联、同义表达、主要/辅助覆盖和历史决定。调研候选、计划和制作任务不创建图谱节点，只有 CMS 重新导入的文章或产品才算已覆盖。候选仍可来自 GSC 信号、图谱缺口或边界扩展；只有全新受众、明显不同用途或站点目的变化才要求边界确认。

## 3. 外部来源与 AI 边界

- `services/external_sources.py` 集中连接能力与来源角色。
- `services/external_evidence.py` 负责 SerpAPI/Tavily/Firecrawl 的用户触发运行、脱敏快照、复用和 evidence ID。
- `services/research_workflow.py` 负责每轮预算、供应商编排、局部失败、精确用量和候选持久化。
- `rules/evidence_workflow.py` 集中外部复核与新文章候选门槛，词项重叠明确标为程序推断。
- `rules/research_workflow.py` 登记多来源调研方法、候选上限、证据边界和 CMS 重叠门槛。
- `services/action_workflow.py` 负责决定基线、有序执行步骤和状态流转。
- `services/settings_store.py` 负责本地设置的验证、原子写入和运行时更新。
- `services/ai.py` 只接收稳定 evidence ID，输出属于 interpretation。
- 路由、模板和规则不直接拼供应商 HTTP 请求。
- 连接测试与数据采集分开；连接成功不产生证据，也不改变分数。
- 外部数据采集只由用户点击触发，24 小时内同口径复用。已有页面的查询级补证据只能使用明确 GSC 查询，不能用标题猜查询；新主题调研可以由 GSC 信号、图谱缺口或已确认分支的边界扩展发起。
- 外部证据可派生新候选和门槛原因，但不回写原 GSC 指标或重算原候选分数。

## 4. 凭据边界

- API Key 只在项目根 `.env` 与后端进程环境中存在。
- `.env` 权限为 `0600`，被 Git 忽略；临时 `.env.tmp` 也被忽略并以原子替换完成写入。
- 密钥不写入 SQLite、HTML、重定向消息或异常日志。
- 设置表单拒绝非 localhost Origin。
- `.env` 未加密，只适用于当前单人本机 WSL。

## 5. 数据库迁移

- v1：站点、导入、GSC、内容、规则、机会、行动、观察和 AI 运行。
- v2：`source_connections`，只保存连接状态、时间、白名单明细和安全错误，不保存凭据。
- v3：`external_runs/evidence_items/action_steps`，以及行动工作流状态、方案版本和完成时间。
- v4：`research_runs/research_run_items/research_candidates`，保存每轮预算、用量、证据关联和待核验主题。
- v5：`imports.analysis_active`，每站点只允许一个 GSC 批次进入当前分析；旧批次仍完整保留。
- v6：`imports.quality_eligible`，把当前机会批次与可累计的可信历史观察窗口分开。

启动时按 `PRAGMA user_version` 增量迁移，用户不需要删除现有数据库。

## 6. 部署方式

第一版监听 `127.0.0.1:8787`。SQLite 与快照位于 `data/`，用户通过浏览器操作。若需要局域网或公网访问，必须另行增加身份认证、HTTPS、备份、CSRF 完整防护和真正的密钥管理。
